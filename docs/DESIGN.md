# Theta Core 设计文档

草案 v0.3，2026-11-06。插件接口见 [PLUGIN_API.md](PLUGIN_API.md)，模型和工具调用的完整约定见 [PROTOCOL.md](PROTOCOL.md)。

## 1. 目标

Eta 社区的 282 个 fork 里，有 55 个带自己的提交，大多在重复改同样的东西：模型提供商、厂商语音助手适配、通知、本地化。改任何功能都要 fork 再自己编译，而且上游的 31 个外部 PR 全部被关了。

Theta Core 要解决这个问题：

- 社区不用 fork，写个插件就能改功能。
- 插件可以随时安装、卸载、更新。卸载时立即撤销宿主注册，彻底清理可能需要重启。
- 内置功能和第三方插件走同一套接口。接口不够用，内置功能先写不出来。

第一版不做的事：

- 不隔离 dex 插件，理由见第 3 节。
- 不做 QuickJS 脚本插件。
- 不做插件之间的依赖，插件只通过扩展点间接协作。
- 不上 Google Play。Play 政策不允许下载可执行代码。
- 不支持旧版 Xposed API，Hook 只走 libxposed Modern API。
- 不开放 `system_server`、SystemUI 等关键进程的第三方 Hook，理由见第 9 节。

代码规则：全新编写，不复制 Eta 和旧 Theta 的代码（旧 Theta 派生自 Eta，受 PolyForm NC 约束）。可以参考公开的协议和标准，比如 OpenAI API、MCP、Agent Skills。

## 2. 架构

```
┌───────────────────── 插件 ─────────────────────┐
│  数据插件  │  MCP  │  dex 插件  │  Hook 插件   │
└───────────────────────┬────────────────────────┘
                 插件 SDK（公开、稳定）
┌───────────────────────┴────────────────────────┐
│ 内核：agent 循环、工具审批、密钥存储、root 桥、 │
│ 屏幕控制执行器、插件管理、安全模式              │
└────────────────────────────────────────────────┘
```

| 目录 | 内容 |
|---|---|
| `sdk/` | 插件 SDK：只有接口和小工具，发布到 Maven Central |
| `core/` | 内核 |
| `app/` | 宿主 App 和“扩展”页面 |
| `plugins/` | 第一方插件：编译进 App，但只用 SDK 接口 |
| `samples/` | 示例插件，同时用作自动化测试的被测对象 |

基本参数：Kotlin + Compose，minSdk 33，targetSdk 跟随当前稳定版。调研里只有 3 个 fork 降过 minSdk，需求不大，所以先不放低。

`applicationId` 用 `io.github.bytejuno.thetacore`，可以和旧 Theta 同时安装。

## 3. 信任模型

dex 插件和 App 同进程，内核防不住它：它能读 API Key，也能直接调 su，因为 root 授权是按 App 的 UID 给的。插件声明的权限只是告知用户，不算防线。这和 LSPosed 模块是同一种信任关系。

| 类型 | 运行位置 | 内核能管住吗 | 风险 |
|---|---|---|---|
| 数据插件 | 没有代码 | 能 | Skill 能引导 AI；提供商配置决定 API Key 发给谁 |
| MCP | App 外 | 能，每次调用都过审批 | 参数会发给对方；对方能改工具定义 |
| dex 插件 | App 进程内 | 不能 | 等同 App 本身，包括 root |
| Hook 插件 | 目标 App 进程内 | 不能 | 等同目标 App，且能影响系统功能 |

内核的安全设计防的是 **AI 乱来**，比如提示注入和误操作。所有**由宿主调度**的工具调用，不管来自内置、MCP 还是插件，都走同一条审批路径。原生插件自行执行的行为不在这个保证内，SDK 是协作约定，不是权限围墙。工具定义一变（用摘要比对），已有授权作废；当前运行中的旧定义调用也不能继续执行，见 PROTOCOL.md 第 3.6 节。MCP 的审批只控制宿主是否发送请求，不保证远端实际行为。

防坏插件靠的是下面这些措施，不是靠隔离：

- 安装时显示作者、签名指纹、声明的能力。数据插件还要显示 API 地址和 MCP 地址的域名。
- 代码插件记住首次安装的签名，更新必须是同一把。无签名数据包不显示“作者已验证”，更新连续性依赖可信索引或用户再次确认来源。
- 默认只信官方索引，其他来源要手动打开开关。
- 不静默更新。
- 卸载挽回不了已经发生的事：已被读走的 Key 要换，用 su 改过的东西要自己检查。确认页要写明这一点。因为不信任而卸载时，要重启 App 完成彻底清理。

## 4. 插件包和安装

**dex 和 Hook 插件**是一个签过名的 APK 文件，但不安装到系统，由 Theta 自己加载。这样能直接用 Android Studio、Gradle 和 apksigner，不用造新工具。清单放在 `assets/theta-plugin.json`。

**数据插件**是一个普通 zip，不用签名，清单放在根目录。写 Skill 的人不需要 Android 工具链。

安装流程：

1. 复制到独立临时目录，解析清单。校验插件 ID，禁止路径穿越和重复 ZIP 条目，并限制解压大小和文件数。
2. 按类型校验：dex/Hook APK 验证整个包的签名完整性并取证书指纹，不只是读取证书；数据 ZIP 校验结构，不要求 APK 签名。
3. 检查 API 等级、插件 ID 冲突、版本号。从可信索引安装的，所有包都比对 SHA-256；代码包另比对签名指纹。
4. 显示确认页。无签名数据包明确标为“作者身份未验证”，不套用代码包的同签名更新规则。
5. 代码包写入 `files/plugins/<id>/<versionCode>/plugin.apk`；数据包写入同版本目录的 `plugin.zip`。Android 14 的动态代码文件要**先创建并打开写入描述符，再设只读，然后通过已打开的描述符写入**。最终落盘内容必须与校验过的内容一致，完整写入并核验后才发布为可启用版本；失败的临时文件不加载。
6. 按类型启用：dex 本进程尚未尝试过该 ID 时才进入类加载路径，更新包只暂存，下一次冷启动激活；Hook 仍遵循目标进程重启规则。数据包只解析并注册数据，不创建类加载器。

未安装的 APK 不会自动向系统注册 Manifest 里的权限、Activity、Service 或 Provider；需要这些能力时由宿主预先提供对应组件和接口。

**类加载器**：每个插件版本一个，父加载器是一层过滤器。

- 先保留完整的 Android boot/platform 类委派，不用包名前缀枚举平台类。`javax.net.ssl.*`、`org.xml.*` 等平台类同样可用。
- 平台类之外，共享包走宿主：`kotlin.*`、`kotlinx.coroutines.*`、`kotlinx.serialization.*`、Compose、SDK。
- 剩余类只在插件自己的包里找。过滤器限制的是宿主应用类的可见性，不阻断平台类加载。插件可以自带 OkHttp 之类的非共享库，版本不和宿主冲突。
- 内核内部类对插件不可见。这是防误用，不是防线，防的是插件依赖内部实现、宿主一升级就坏。

**资源**：dex 插件不使用 Android 资源表（`R` 类）。插件 APK 和宿主默认都用 `0x7f` 这个资源包 ID，混用容易冲突。图片和文字放 `assets/`，通过 SDK 读取。

## 5. 生命周期

**已批准的生命周期决策（2026-11-06）**：原生 dex 保持全信任、同进程执行，不新增隔离层或 API。停用是持久化意愿、撤销宿主注册、取消作用域和有界等待回调，不是强制停止或热卸载。该决策取代旧稿的“普通 dex 更新立即启用”“不重启完整卸载再安装”和“必须回收类加载器”要求；第 11 节保留原验收范围及变更对照，不把变更记作验收通过。

三个词在全文里含义固定：

- **撤销宿主注册**：立即移除插件的工具、提供商、界面、后台任务登记，阻止宿主发起新的调度；不等待插件回调完成，也不表示已经在运行的调用停止。
- **彻底清理**：插件的代码和它留下的线程、回调、静态引用真正离开内存。宿主只能观察，不能保证。能保证的只有重启进程。
- **判定失败**：宿主不再等待，按失败处理。这不代表插件已经停止。

```
已安装 ──启用──▶ 运行中 ──停用──▶ 已停用 ──卸载──▶ 已删除
             │        │
             ▼        ▼
          启用失败   被隔离（反复出错或安全模式）
```

状态之外还有一个“**待重启**”标记：进程内已经尝试加载的原生插件 ID，在进程重启前不再创建第二个实例，包括初始化失败、超时、停用或卸载后重新安装。重新启用只保存下次冷启动的意愿；GC 结果不解除这个门控。上图中的“已删除”对已加载插件须经过持久化删除标记和冷启动清理，不是进程内热卸载。

**注册追踪**：插件的工具、提供商、界面、后台任务都通过 `PluginContext` 注册。开始停用时，宿主先持久化停用意愿，再与 `register`、`onCleanup` 原子地关闭注册入口并取走已有登记，撤销扩展、取消插件作用域，在独立清理任务中调用 `onDisable`，再逆序执行 cleanup。并发登记必须满足“关闭前成功并纳入本次清理”或“关闭后抛 `PluginClosedException`”之一，不能漏在两者之间。调用插件代码时不持有注册表锁，避免回调重入死锁。启用抛异常或超时也走同一套关闭与撤销流程。清理任务不挂在已经取消的插件作用域下；有界的是宿主等待时间，不承诺每个非协作回调都能执行完毕。

**超时**：初始化、清理和单次工具调用有时限，模型流按 PROTOCOL.md 的首事件和空闲时限处理。`EntryAdapter.attach` 是插件作用域中的常驻任务，不设整个监听期的总超时；它的初始化有独立时限，见 PLUGIN_API.md 第 4 节。**超时判定失败，不保证终止非协作代码。**

- 宿主会取消协程并不再等待。阻塞线程、死循环、JNI 调用不响应取消，可能继续运行，也可能继续产生副作用。
- 同一进程里没有安全的办法强杀线程，可靠的终止方式只有重启进程。
- 宿主调度的插件任务使用独立、有界的执行资源，不能只用共享线程池的并发视图冒充阻塞隔离。插件自行创建线程或阻塞主线程不在这项保证内。
- 工具的逻辑超时不释放尚未确认停止的执行实例及资源租约。资源隔离、外部操作未知和恢复规则见 PROTOCOL.md 第 3.7、3.8 节；这些约束只作用于宿主调度。
- 插件卡住主线程时，宿主连判定都做不到，结果就是 ANR。

| 超时的位置 | 判定 | 之后的处理 |
|---|---|---|
| `onEnable` | 启用失败 | 撤销已有注册，标记待重启 |
| `onDisable` | 清理失败 | 继续撤销注册，标记待重启 |
| 工具调用 | 调用超时 | 结果标记“副作用未知”，见 PROTOCOL.md 第 3.8 节 |
| 模型请求 | 请求超时 | 按错误处理，见 PROTOCOL.md 第 2.8 节 |

**停用和卸载：**

- 停用意愿保存后立即关闭登记并取消作用域，不以等待 agent 当前轮次结束为前提。正在运行的工具仍受执行租约约束：撤销注册和逻辑超时都不释放尚未确认停止的实例及资源租约，也不保证非协作代码停止。
- 打开着的插件页面先退回上一级，再撤销注册。
- 依赖它的会话和定时任务标记为“不可用”，不崩溃。如果被卸的是当前提供商，提示用户换一个。
- 卸载时明确询问保留还是删除插件数据，默认保留，只有用户明确选择才删除数据。已加载插件先持久化删除标记（tombstone），撤销注册并取消作用域，下一次冷启动在加载插件前删除包及用户选中的数据；未加载插件可以立即删除。同进程尝试加载过的 ID 仍不能再次实例化。

| 插件 | 安装 | 卸载或停用 | 更新 |
|---|---|---|---|
| 数据插件 | 立即生效 | 立即撤销宿主注册，不需要重启。已写进对话的内容不会撤回 | 下一次运行生效 |
| MCP | 立即生效 | 立即撤销宿主注册并断开连接。对方已开始执行的调用不保证停止 | 下一次运行生效 |
| 普通 dex | 本进程未尝试过该 ID 时可启用，否则等冷启动 | 持久化意愿后立即撤销注册、取消作用域；已加载包卸载标记后冷启动删除 | 新路径暂存新版本，保留旧运行实例，下次冷启动启用 |
| 带 `.so` 的 dex | 同普通 dex | 同普通 dex，不保证卸载 native 库 | 同普通 dex，必须重启 App 才启用新版本 |
| Hook | 目标进程重启后生效 | 立即撤销宿主注册，回调改为放行。代码要等目标进程重启才退出 | 目标进程重启后生效 |

**残留观察**：弱引用和 GC 只能作为诊断信息，不是停用成功条件，也不是允许同进程重新加载的依据。不承诺热卸载或类加载器必定被回收；代码退出内存依赖相应进程退出。宿主管不到插件自己开的线程和静态引用。

**崩溃处理：**

- 宿主受管调用的可捕获异常应归因并计数，短时间内反复出错应自动隔离；不覆盖任意后台线程或 native 崩溃。
- 宿主管理的插件协程异常捕获与恢复仍是 S1 D 的要求，不因采用全信任同进程模型而豁免，也不能由登记清理测试代替。
- 插件自己开的线程和 Compose 组合期的异常可能让 App 崩溃。Compose 不允许用 try/catch 包住可组合函数的调用；这类崩溃需要第 7 节的冷启动恢复。完整故障注入和恢复尚未验收，不能把恢复启动入口可用等同于自动崩溃恢复通过。

## 6. 更新和回滚

**流程（原生 dex 的更新以冷启动切换为准）：**

1. 校验新包并写入新版本路径，持久化待更新状态，不覆盖旧包，也不在当前进程启用新版本；旧运行实例保留到停用或进程退出。
2. 下一次冷启动，在加载任何插件前处理删除标记和待更新状态，对宿主管理的旧数据做快照。不能以 `onDisable` 返回或 GC 观察作为旧代码已停止写数据的证明。
3. 从新路径加载新版本。一次进程生命周期内同一 ID 只尝试实例化一次。
4. 进入观察期，默认 24 小时。观察期结束才删除旧文件和快照。

**什么时候回滚（仍待实现和验收）**：启用失败时应安排自动回滚，但已尝试加载该 ID 的进程不能立即再实例化旧版本，恢复数据及启用旧版本须到下一次冷启动。观察期内被隔离或进入安全模式时，提示用户回滚；用户也可以在观察期内手动回滚。以下快照、观察期和恢复边界仍是原设计要求，不是当前原型已实现的能力；S1 F 未完成。

**回滚的数据边界：**

| 内容 | 能否恢复 |
|---|---|
| 插件代码和清单 | 能 |
| `dataDir`、`prefs`、`secrets` | 能，恢复到更新前的快照。更新之后写入的内容全部丢弃 |
| 对话记录、审批记录、工具调用账本 | 不回滚。这些属于内核，是已经发生的事实 |
| 已执行的工具调用的副作用 | 不能 |
| `dataDir` 之外的文件、共享存储、系统设置、su 做的改动 | 不能 |
| 远程服务的状态、已发出的请求和消息 | 不能 |
| 新版本已轮换的 OAuth Token | 快照里的旧 Token 可能已失效，要重新登录 |
| 没有通过 `onCleanup` 登记的系统注册（闹钟、广播接收器等） | 不能 |
| Hook 插件在目标 App 里留下的数据 | 不能 |
| 运行中的目标进程 | 要等目标进程重启，才回到旧版本 |

**几条规则：**

- 快照只覆盖宿主管理的数据。更新确认页要写明这条边界。
- 空间不足或快照失败时默认取消更新。用户可以选择不做快照继续更新，但之后回滚只恢复代码，旧版本可能读不了新数据。
- 新版本卡死、无法确认已停时，不原地恢复数据，因为它可能还在写。这时标记待重启，下次冷启动在加载任何插件之前恢复快照。
- 插件的数据库和文件要在 `onDisable` 里关闭，否则快照可能不一致。
- 观察期结束后不能回滚。想用旧版本只能卸载、删除数据、重新安装，因为 `versionCode` 只升不降，防止旧代码读到新格式的数据。
- 数据插件和 MCP 没有私有数据，回滚只换回旧文件和配置。

## 7. 安全模式和恢复

Theta 的安全模式只管 Theta 自己的进程。Hook 代码跑在目标进程里，由 LSPosed 加载，不经过 Theta 的 App 进程。Theta 崩溃、没在运行或处于安全模式时，这些代码都可能继续运行。所以 Hook 要有一条**不依赖 Theta 运行**的恢复路径。

### 7.1 Theta 进程

- **进入**：启动后短时间内连续崩溃两次，下次启动自动进入。桌面长按图标也提供“安全模式启动”的入口。
- **进入后**：必须冷启动才可在加载前跳过 dex 和 Hook 插件；向已有进程发送恢复请求不会卸载现存代码。列出嫌疑插件，并打开全局开关暂停所有 Hook（见 7.2 第 3 层，完整 Hook 路径仍待验证）。
- **还是崩溃**：再下一次连数据插件和 MCP 也不加载。
- **运行中的目标进程**：安全模式页列出已经加载过 Hook 的目标 App，并提供重启入口（见 7.2 第 4 层）。
- **退出**：保存恢复意愿，下一次普通冷启动只恢复没有嫌疑的插件。嫌疑插件保持隔离，由用户逐个启用，仍遵守同进程不二次实例化规则。

以上是完整恢复设计。当前增量仅记录手动恢复冷启动跳过、未完成初始化标记的保守禁用等能力，不等同于连续崩溃检测、受管协程和 Compose 崩溃恢复全部通过；验收缺口见 S1_VALIDATION.md。

### 7.2 目标进程和 Hook

| 层 | 解决的问题 | 做法 | 依赖 |
|---|---|---|---|
| 1 回调保护 | Hook 回调抛异常 | SDK 包装层捕获异常，放行原方法并计数。超过阈值，就在这个进程里停用这个插件 | 目标进程 |
| 2 崩溃循环检测 | 插件让目标 App 反复崩溃，包括 native 崩溃这类捕获不到的情况 | 模块入口在加载插件之前写启动计数，进程稳定运行一段时间后清零。短时间内连续崩溃 3 次，下次启动跳过这个插件 | 目标进程 |
| 3 全局开关 | Theta 决定暂停某个或全部 Hook | Theta 通过 `XposedService` 写远程偏好，模块入口和 SDK 包装层读取 | Theta 能打开 |
| 4 重启目标进程 | 让 Hook 代码真正退出 | 有 root 时执行 `am force-stop`，没有 root 时跳到 App 信息页由用户强停 | root 或用户操作 |
| 5 框架外恢复 | Theta 打不开，或前面几层都挡不住 | 在 LSPosed 管理器里停用 Theta Core 模块或移除目标作用域。再不行就在 KernelSU、Magisk 里停用 LSPosed，或者用 adb 卸载 Theta Core | 框架或 adb |

**为什么第 2 层写目标 App 自己的目录**：libxposed 的远程偏好和远程文件在被 Hook 的进程里都是只读的，隔离状态写不进去。所以计数放在目标 App 的设备加密存储里，这样解锁前也能用，而且不需要 Theta 在运行。

**隔离记录**：第 1、2 层隔离后，等回调通道可用时报告给 Theta，由“扩展”页面显示“插件 X 在 Y 上被隔离”。隔离按插件版本和目标 App 版本记录，任何一方更新后自动重试一次。

**覆盖范围**：第 1、3 层只管通过 `env.hook` 注册的回调。插件自己开的线程和绕过 SDK 的 Hook 不受影响，要靠第 4 层。第 3 层生效的延迟取决于目标进程能否监听远程偏好的变化，这一点还没验证（见第 12 节）。

**为什么要限制目标**：如果 Hook 把系统界面或 LSPosed 管理器弄崩，用户就连第 5 层的入口都没了。所以第三方 Hook 第一版只开放普通 App 进程，见第 9 节。

## 8. 兼容性

**API 等级**：SDK 用一个递增整数。宿主声明支持的最低和最高等级，超出范围的插件不加载，也不尝试运行。

**SDK 演进规则：**

- 同一主版本内只增不删。CI 用 ABI 校验工具比对，有破坏性改动就失败。
- 接口新增的方法必须有默认实现。
- 公开 API 不用 `data class`。加字段会改变构造函数和 `copy` 的签名，破坏二进制兼容。
- 宿主传给插件的对象用接口，插件传给宿主的对象用 builder。

**共享库**：Kotlin、协程、序列化、Compose 由宿主提供，插件不打包。每个 API 等级对应一份 BOM，插件编译时用的版本不能高于宿主。插件只能用这些库的稳定 API，不能用 `@Experimental*`。

**R8**：这是最大的工程风险。正式版宿主经过 R8 后，共享库的类可能被改名或删除，单独编译的插件就链接不上。计划用 keep 规则保住共享库的公开 API，但这会让 App 变大，也可能影响 Compose 性能。S1 实测后，按下面的顺序选方案：

1. keep 全部共享库的公开 API。
2. 只 keep Compose 的 runtime、ui、foundation、material3，其余共享库由插件自带。
3. 插件只能用 SDK 封装的界面组件。
4. dex 插件不写 Compose，改用声明式界面，由宿主渲染。

## 9. Hook 插件

Hook 是厂商适配的主力，调研里相关改动有 28 个 fork、33 个 issue，也是最容易随系统升级失效的部分。

**架构**：Theta Core 本身是 LSPosed 模块，框架在每个目标进程里创建一个模块实例。模块入口读取清单，把对应的 Hook 插件加载进目标进程。Hook 插件依赖完整的 Xposed 框架，不支持嵌入式框架，因为后者没有远程文件能力。

**代码怎么进入目标进程**：目标进程读不了 Theta 的私有目录。Theta 通过 `XposedService` 的 `openRemoteFile` 把插件包写入模块共享目录，目标进程用 `XposedInterface` 的 `openRemoteFile` 只读打开，读进内存后用内存类加载器加载。共享目录的文件名不能带路径分隔符，所以用 `<插件ID>-<versionCode>.apk` 这样的平铺命名。这些接口在 libxposed 的源码里都有，但整条路径还没实测，放在 S1 验证。

**作用域**：安装 Hook 插件时，通过 `XposedService.requestScope` 申请目标 App 的作用域，由框架向用户确认。

**规则和代码分开**：DexKit 匹配规则按目标 App 的版本范围存放，可以作为数据单独更新。小爱或小布升级后，多数情况只需要更新规则，不用发新代码。

**停用**：SDK 提供的 Hook 包装层在回调里检查开关，停用后放行原方法，代码等目标进程重启才退出。

**回调通道**：目标进程回到 Theta 的调用必须校验调用方。上游 issue 里有 `XposedProvider` 全局导出、不校验调用方的安全问题，这里不能重犯。

**目标限制**：第三方 Hook 第一版只开放普通 App 进程。下面这些目标不开放：

- `system_server`：出错可能卡在开机。
- SystemUI（`com.android.systemui`）、设置（`com.android.settings`）：出错可能让手机无法操作。
- 当前桌面：出错可能让手机无法操作。各家 ROM 的包名不同，运行时查询默认桌面。
- 电话：通话服务 `com.android.phone` 和默认拨号 App 都算，出错可能打不了电话。
- LSPosed 管理器和 Theta Core 自己：出错会破坏第 7 节的恢复入口。

默认桌面和拨号 App 可能在安装之后改变，所以安装时和加载时都要检查。加载时命中受限目标的，这次不加载，并在“扩展”页面提示。

电源键接管这类需要 `system_server` 的功能，先由第一方实现，并且要先有“连续启动失败就跳过插件”的救援机制。这个机制做好之后，再考虑对第三方开放。

## 10. 其他设计

**语言包**：Android 资源里的字符串无法被插件覆盖，所以界面文字从第一天起就走统一的字符串表，语言包按键值覆盖。这件事后补的代价很大。

**第一方插件**：内置功能写在 `plugins/` 下，只依赖 SDK，编译进 App，生命周期和第三方相同，但不走动态加载。

**分发**：

- 索引仓库 `ByteJuno/theta-plugins`，内容是一份 `index.json`，记录插件 ID、类型、版本、下载地址、SHA-256、源码仓库和 commit。代码包必须记录签名指纹，无签名数据包的该字段为空。
- 收录要求：公开源码，通过 PR 审查，构建产物由 GitHub Actions 从源码生成，并附 artifact attestation。
- 模板仓库 `ByteJuno/theta-plugin-template`：fork 后改代码，Actions 直接出插件包。
- 插件仓库加 `theta-plugin` 这个 GitHub topic，方便发现。
- SDK 发布到 Maven Central。GitHub Packages 读取也要登录，对社区不友好。

**性能要求**：

- 长对话按需加载，不把全部会话留在内存；每轮增量写入，不全量写库。S2 的聊天和存储按此实现。
- 流式输出按帧合并后再刷新界面，不按收到的每段文字刷新。S2 实现。
- 插件增多后的冷启动时间要实测。S4 开放生态之前，用批量测试插件在固定真机上记录不同插件数量下的耗时。

## 11. 里程碑

所有构建都在 GitHub Actions 上跑，不在本地跑 Gradle。

**S0 工程骨架**：Gradle 多模块、PR Check、发布签名。

**S1 可行性验证**：决定方案成败的一步，先做。空宿主 + 示例插件，适用验收项及补充断言全部通过才进 S2。S1 尚未完成；这次文档协调不是验收结果。

**原始验收范围（历史保留）**：下表保留旧稿 A–K 原文。B 的不重启链路和 C 的强制 GC 已被批准决策明确取代，不能继续作为现行承诺，也不能记为通过；现行断言见表后对照。其余项目未被取消。

| 编号 | 原始验收项 | 怎么测 |
|---|---|---|
| A | 开了 R8 的正式版宿主，能加载单独编译的插件并显示其 Compose 设置页 | CI 模拟器 |
| B | 不重启完整跑通“安装 → 使用 → 卸载 → 装新版本” | CI 模拟器 |
| C | 卸载后旧类加载器能被回收 | CI 模拟器 |
| D | 插件在启用时、工具调用时、Compose 里分别抛异常，App 都能恢复 | CI 模拟器 |
| E | 不响应取消的插件超时后，宿主判定失败、标记待重启，App 继续可用 | CI 模拟器 |
| F | 更新失败时恢复快照；新版本卡死时，改到冷启动时恢复 | CI 模拟器 |
| G | 量化 keep 规则对 APK 体积和界面帧耗时的影响 | CI + 真机 |
| H | 不把共享库打进插件的 Gradle 配置可用 | CI |
| I | 不安装的 APK 能在设备上校验签名、取到指纹 | CI 模拟器 |
| J | Hook 插件经远程文件进入目标进程并生效，`requestScope` 可用 | 真机 |
| K | 目标 App 崩溃循环后自动跳过插件，全局开关和框架外恢复路径可用 | 真机 |

**批准决策后的现行断言对照：**

- B：安装/使用后，停用先持久化意愿，再撤销登记、取消作用域、有界等待回调；已尝试 ID 在重启前不二次实例化。更新新路径暂存、冷启动激活；已加载卸载先写 tombstone、冷启动删除，数据默认保留且删除须明确选择。真实升级包切换、异常包路径仍需设备验证。
- C：不再要求 GC 成功或热卸载；检查撤销登记、冷启动清理及进程内门控，不用弱引用结果解除门控。这是要求变更，不是旧 C 测试通过。
- D/E：仍须验证受管协程、工具、Compose 故障恢复，以及非协作代码超时后的宿主可用性和执行资源预算；仅免除强停原生代码的承诺，不免除这些门槛。工具资源租约和冷启动隔离记录依赖调用账本，改到 S2 验收。
- F：保留快照、更新失败回滚和卡死后冷启动恢复要求，回滚同样遵守不二次实例化；尚未完成。
- A/G/H/I/J/K 和下列补充断言继续有效；签名补丁未在本次验证，真机性能与 Hook 远程加载、作用域及救援门槛均不能以原型通过代替。逐项证据缺口见 S1_VALIDATION.md。

S1 的补充断言（并入现有项目，不新增里程碑）：

- A/H：插件自带 OkHttp 发起 HTTPS 请求，验证 `javax.net.ssl` 等平台类不被宿主过滤器拦截。
- B/I：无签名数据 ZIP 可正常安装，代码 APK 仍验证签名；无效包、写入中断和摘要不符均不能激活。
- B/D：在关闭注册入口的边界并发调用 `register` 和 `onCleanup`，只允许成功纳入清理或拒绝，不能遗留扩展；启用失败采用同一规则。
- D/E：入口初始化超时判失败，但 ready 后持续运行超过普通调用时限仍能收到事件；停用后监听器释放。
- E：非协作代码超时后，宿主判定失败并标记待重启；判定不依赖实例返回，实例实际退出前不按已退出处理。

**S2 最小 agent**：按 PROTOCOL.md 实现 OpenAI 兼容提供商、聊天界面、一个工具、审批流程和调用账本。验收包含从 S1 的 E 挪来的断言：非协作 screen 工具逻辑超时后，同资源的另一会话也不能开始；实际退出才释放本地租约，外部状态未知时冷启动仍保留隔离记录。

**S3 五类扩展点**：模型提供商、工具（含 MCP）、入口适配器、输出位置、数据插件。同时把 S2 的内置功能改成第一方插件。

**S4 生态**：扩展页面、索引仓库、模板仓库、SDK 发布。

**S5 功能追平**：按日常使用的优先级迁移功能，够用之后替换旧 Theta。

| 假设 | 不成立时的影响 |

## 13. 已确认的默认值

2026-11-06 确认：

1. App 显示名：开发期叫 “Theta Core”，和旧 Theta 区分。
2. minSdk 33。
3. 第一版不开放第三方 Hook 关键进程（第 9 节的列表）。
4. S1 按第 11 节保留的 A–K 范围及补充断言验收，B/C 使用明确批准的替代断言；其余门槛不减免（E 的调整见第 7 条），全部适用项通过才进 S2。

6. 插件生命周期采用重启模型（第 5 节）：更新、停用后再启用、卸载后重装同一插件，都在重启 App 后生效。
