# S1 disposable fixtures

These extend the existing `:samples:fixtures` module. No root settings/build change is needed.
Existing r5 flavor definitions, `FixturePlugin.kt`, plugin ID, metadata and behavior are unchanged.
S1 code is in `src/s1/kotlin`, included only by S1 flavors. All S1 flavors share the separate
plugin ID `io.github.bytejuno.thetacore.sample.fixture.s1`, entry
`io.github.bytejuno.thetacore.sample.fixture.s1.S1FixturePlugin` and log tag `ThetaS1Fixture`.
The original nine flavors plus `s1EntryLongReady` and `s1SettingsComposeCrash` are version
1.0/code 1; `s1SettingsV2` and `s1SettingsFailV2` are version 2.0/code 2. Use one S1 flavor at a time. Uninstall before switching equal-version
scenarios, but **do not uninstall or clear data during the V1 → V2 rollback tests below**.
Do not clear host data if preserving r5 test state.

## Entry scenarios

Extension ID: `s1-entry`. The manager attaches automatically on registration. The fixture
checks that `displayName`, `isAvailable` and `attach` run off Main; violating that produces
`S1 plugin callback on Main` instead of a false pass.

| Flavor | Fixture markers | Required host observation |
| --- | --- | --- |
| `s1EntryReady` | `entry:ready:sent`; on disable `entry:attach:finally` | INITIALIZING → READY; disable removes the entry from public UI. STOPPED/actualExited are unobserved there. No chat backend is claimed. |
| `s1EntryLate` | `entry:late:block:start`; at ~60s `entry:late:ready:attempt`, `entry:late:ready:return`, `entry:attach:finally` | At the current 30s init deadline, UNAVAILABLE. The late `ready()` must NOT resurrect READY. Finally is later than timeout, but is not host actualExited evidence. |
| `s1EntryNonCooperative` | `entry:ready:sent`, `entry:noncooperative:block:start`; at ~60s `entry:noncooperative:block:end`, `entry:attach:finally` | Disable while blocked: UI remains responsive and entry registration disappears. Public UI cannot show the retired runtime's STOPPED/actualExited; execution-budget acceptance remains separate and unverified. |

`SystemClock.sleep(60_000)` ignores interrupts/cancellation but is finite. Run blocking cases
serially and wait for `finally` (or restart the disposable host) before the next case.
A fixture log records a callback attempt; only the host state proves admission or rejection.

## Tool scenarios

Extension ID: `s1-tool`; spec name `s1_fixture`; invoke with `{}`. Use the host's
`PluginManager.invokeTool(pluginId, registeredTool, JsonObject(emptyMap()))` boundary, then
observe `PluginInvocation.spec`, `progress`, `terminal`, and `actualExited`.
Do not call `tool.call` directly: that skips admission/deadline behavior being tested.
The fixture's `tool.spec` and `tool.call` both assert off-Main execution.

At implementation inspection, MainActivity had no tool/entry invocation controls. A host UI
or in-process acceptance harness must supply the above invocation/state-observation surface;
this fixture does not expose a shell/debug RPC or silently invoke a tool from its settings page.
That app/harness integration is outside this module's ownership. Any host UI must display
host-owned snapshots, not evaluate arbitrary Tool getters on Main.

| Flavor | Fixture markers/result | Required host observation |
| --- | --- | --- |
| `s1ToolSuccess` | `store:write:verified:tool`, `tool:success`; `S1_TOOL_OK`, structured marker `S1_TOOL_OK`, APPLIED | SUCCEEDED. Settings refresh displays `S1_PREF_tool` and `S1_SECRET_tool_DISPOSABLE`. |
| `s1ToolThrow` | `tool:throw`, `tool:call:finally` | FAILED, not a host process crash; other settings actions still work. |
| `s1ToolBlock` | `tool:block:start`; ~60s later `tool:block:end`, `tool:call:finally` | TIMED_OUT near 2.5s, actual exit still pending. Late progress `S1_LATE_PROGRESS_MUST_BE_IGNORED` and result `S1_LATE_RESULT_MUST_BE_IGNORED` must not replace terminal/progress state. |
| `s1ToolProgress` | Five `tool:progress:N/5` ticks, `tool:progress:success`; `S1_PROGRESS_OK` | Progress fractions 0.2 through 1.0; SUCCEEDED after ~5s despite 2.5s idle deadline, because 1s heartbeats refresh it. |

Timing allows scheduling tolerance. All calls include `callId` in start/finally logs for
correlation. Cancellation can be checked by cancelling progress while it runs: expect one
CANCELLED terminal plus finally, without a later success. Don't interpret every fixture
`finally` as SUCCEEDED. The tool progress flow may conflate intermediate ticks; logcat
records all five emissions, while UI is only required to show current progress.

## Prefs / secrets page

Every successful S1 enable registers `s1-settings` titled **S1 fixture settings** (`s1SettingsFailV2`
throws before registration). `s1Settings` registers only this page. For the original nine
flavors, first enable seeds missing values; later enables never overwrite writes.
All synchronous SDK store reads/writes run on Dispatchers.IO; Compose displays an immutable
snapshot, not storage or tool getters.

1. Open the page: expect `S1_STORE_OK`, `S1_PREF_SEED`, `S1_SECRET_SEED_DISPOSABLE` on fresh data.
2. Press **Write S1 prefs and secrets**: expect `store:write:verified:page`, `S1_STORE_OK`,
   `S1_PREF_page`, `S1_SECRET_page_DISPOSABLE`.
3. Leave/reopen; disable/re-enable; cold-restart host: values must remain the same. **Refresh
   S1 values** reloads actual SDK storage (including writes from `s1ToolSuccess`), not cached text.
4. `S1_STORE_ERROR:<type>` is a failure, not an absent value/success. Each store operation is
   atomic; the two stores together are deliberately not described as one transaction.

Only fixed, synthetic disposable strings are displayed; no real account tokens are needed.

### Normal update: once-only writes

Start with enabled `s1Settings` V1, either seeded values or press **Write S1 prefs and secrets**
to establish `S1_PREF_page` / `S1_SECRET_page_DISPOSABLE`. Record which pair is the baseline.
Import `s1SettingsV2` as an update, keeping the same ID and signing identity. First enable:

- `settings:update:v2:start`
- `store:write:verified:v2`
- `settings:update:v2:applied`, then `enable:return`
- Page runtime `s1SettingsV2`, values `S1_PREF_v2` / `S1_SECRET_v2_DISPOSABLE`.

The migration uses separate prefs key `s1.migration.settings-v2 = done`, committed **after**
both values are written and read back. It does not infer migration from the existing value
of `s1.preference`. This key lives in the same snapshotted data as ordinary prefs. On a
later enable, expect `settings:update:v2:already-applied` with no new migration writes.
Press the page write button, restart/re-enable V2, and verify `S1_PREF_page` /
`S1_SECRET_page_DISPOSABLE` survive. This is a separate durability check; for rollback value
contrast, use a fresh V1 → V2 run and do not press write after the migration.

### Manual snapshot rollback

In a fresh run, establish V1 baseline and update to V2 **with data snapshot**. Confirm V2
values, then request the host's manual rollback **with snapshot restoration**:

- Running page returns to `s1Settings` (V1 code).
- Both preference and decrypted secret exactly match the recorded V1 baseline, not `v2`.
- The V2 migration marker must also be restored to its pre-update absent state. Verify
  behaviorally by updating to V2 again with a snapshot: expect `v2:start` and `v2:applied`,
  not `v2:already-applied`, even if the baseline happened to contain similar ordinary values.

### Explicit code-only rollback

Repeat from a fresh V1 baseline. Use the host's explicitly selected **code-only / no data
snapshot** update option, update to normal V2, and verify the V2 values before rollback.
Rollback using the corresponding explicit code-only path (not a failed attempt to restore
an unavailable snapshot). Expected V1 runtime `s1Settings`, **retained** `S1_PREF_v2` /
`S1_SECRET_v2_DISPOSABLE`, and retained migration marker. V1's seed must not overwrite them.
Re-upgrading this retained-data installation to V2 should log `v2:already-applied`.
Do not report code-only rollback as data rollback: the preserved V2 values are intentional.

### Failing V2 automatic rollback

In a separate fresh V1 baseline run, import `s1SettingsFailV2` **with data snapshot**. Its
onEnable writes and reads back distinct `S1_PREF_fail_v2` / `S1_SECRET_fail_v2_DISPOSABLE`,
then emits `settings:update:fail-v2:written`, `settings:update:fail-v2:throw` and throws
`S1_SETTINGS_FAIL_V2_AFTER_WRITES`. It does not register a page or emit `enable:return`.
Require the host's automatic rollback to restore V1 code and BOTH baseline values;
`fail_v2` values must not survive, and the host process must stay alive. A rejection before
`fail-v2:written` does not exercise damaged-data rollback and is not a pass.

For an additional explicit code-only failing-update run, select no snapshot deliberately:
if the host admits this mode, automatic code rollback should leave the two `fail_v2` values
in place under V1. If the host rejects this mode, record the rejection; do not fabricate a
rollback pass. Keep this result separate from the snapshot recovery acceptance.

## Deliberate settings-page crash / recovery

Use `s1SettingsCrash` on a disposable app instance. It behaves like the normal settings page
until the explicit **Crash S1 settings page** button. The button logs `settings:crash:armed`
and throws `IllegalStateException("S1_SETTINGS_PAGE_CRASH")` uncaught on Main. This is a
real process-crash probe, not a managed coroutine failure, force-stop, or enable failure.

1. Import/enable, open **S1 fixture settings**, write the two test values, then click crash.
2. Require both the armed marker and AndroidRuntime `S1_SETTINGS_PAGE_CRASH`/process exit.
   A marker alone is not crash evidence. Do not clear app data between crash and relaunch.
3. Cold-launch the same host:

   ```sh
   adb shell am start -W -n io.github.bytejuno.thetacore/.MainActivity
   ```

4. Require the host to identify `io.github.bytejuno.thetacore.sample.fixture.s1` as the
   suspect page owner and skip its automatic restore. There must be no new S1
   `enable:start` on that launch before explicit re-enable. Unrelated r5 plugin state
   must remain intact. The fixture does not itself decide or clear recovery policy.
5. Explicitly re-enable the suspect through the host, reopen the page, and verify retained
   `S1_PREF_page` / `S1_SECRET_page_DISPOSABLE`. Re-enabling should acknowledge the suspect.
   Do not press crash again unless testing the recovery escalation sequence separately.

## Genuine composition-time crash on opening (D)

New flavor `s1SettingsComposeCrash`, version 1/code 1, dedicated plugin ID
`io.github.bytejuno.thetacore.sample.fixture.s1.compose` and name `S1 Composition Fixture`.
This isolates the required fresh baseline without deleting retained data from the other S1 fixtures.
Older candidate12 artifacts used the shared S1 ID and must not be used for this fresh-data case. The existing
`s1SettingsCrash` **button callback** scenario remains unchanged and does not prove a
composition-time exception. Build/import the new flavor using the tasks/artifacts above.

This flavor **never calls seed()**, including on recovery enable. On the first settings
open, bounded IO reads prefs key `s1.compose-crash.consumed`. With no claim, it requires
both ordinary values absent (fresh fixture data), then writes and reads back the distinctive
fixed synthetic baseline at `s1.preference` and `s1.secret`:

- `S1_PREF_compose_baseline`
- `S1_SECRET_compose_baseline_DISPOSABLE`

Expected values are code constants, not inferred from recovered data or seed defaults.
After BOTH readbacks, `compose:baseline:persisted` is emitted; only then is
`consumed:<instance UUID>` persisted/read back and `compose:marker:persisted` emitted.
The effect sets in-memory state to armed. The next composition of `BeforeContent`, called
directly from `SettingsPage.Content`, emits `compose:throw:before` and throws
`IllegalStateException("S1_SETTINGS_COMPOSITION_CRASH")`.
**No button is pressed; neither the effect coroutine nor onEnable throws this exception.**
The loading composition keeps synchronous SDK disk IO off Main and withholds the ordinary
page until the gate finishes. A retained claim takes a strictly read-only verification path:
missing, seed, wrong or unreadable prefs/secrets produce `compose:baseline-or-marker:error`
and visible `S1_COMPOSE_BASELINE_OR_MARKER_ERROR`, never `S1_COMPOSE_RECOVERED`. There is no
repair write or re-arm on this path. A malformed claim also fails visibly.

1. Use fresh fixture data on a disposable host: claim and both ordinary values absent.
   Enable (no seed writes), start continuous log capture, then open settings. The fixture
   establishes the pair above automatically; no preliminary page-write action is needed.
2. Require same-instance `store:write:verified:compose_baseline`,
   `compose:baseline:persisted`, `compose:marker:persisted`, `compose:throw:before` in order,
   followed by AndroidRuntime crash/stack containing `S1_SETTINGS_COMPOSITION_CRASH` in the
   composable path. Keep the original claim and expected pair in the external run record.
   A marker, coroutine failure, force-stop, or button exception is not a pass. The inspected
   host journals page ownership BEFORE calling Content; the fixture does not fake this policy.
3. Cold-launch the same host without clearing data:

   ```sh
   adb shell am start -W -n io.github.bytejuno.thetacore/.MainActivity
   ```

   Require S1 identified as suspect, automatic restore skipped (no new `enable:start` before
   explicit enable), host UI usable, and unrelated plugins preserved. Record exit/new pid.
4. Explicitly enable via the host recovery action, reopen settings. Require
   `compose:marker:retained` and `compose:baseline:retained` with the ORIGINAL claim,
   `compose:recovery:rendered` with the new instance/pid, visible `S1_COMPOSE_RECOVERED`,
   `S1_STORE_OK`, and the exact pair above. No `store:seeded`, baseline-write/persisted marker,
   new claim or second deliberate crash is permitted on recovery.
5. Click **Refresh S1 values**, then leave/reopen. Require the same pair and read-only
   validation again, without a second exception. This flavor hides the ordinary write button
   so the evidence baseline cannot be accidentally overwritten. Use `s1Settings` separately
   for the ordinary write-button test; it is not part of this crash-recovery run.

One extra prefs key persists until deletion or snapshot restoration. With the claim retained,
re-enabling/reopening/rebooting does NOT re-arm, even when either value is lost or corrupt.
An absent claim with surviving values fails the fresh-data guard instead of repairing them.
Total loss of claim AND both values is indistinguishable locally from a fresh installation:
a new first-run attempt can occur, but the original-claim/no-new-write recovery criteria MUST
fail; never count that new attempt as recovery. Keep the external pre-crash evidence.
No data deletion or flavor switching is allowed during recovery. Separate stores are not a
transaction; interrupted baseline establishment is not a pass. Persistence-before-throw also
leaves a narrow interruption window: if navigation/death happens after claim but before throw,
next open is consumed without a crash. Require the full marker sequence AND actual crash
stack; a consumed marker alone never counts. For another first-crash test use fresh data.

The original additions included flavor declarations in `build.gradle.kts`. This evidence
correction changes only this document and the two S1 Kotlin source files; no host production
instrumentation, build/config changes, builds, Gradle configuration runs, devices, adb,
commits or pushes were used for this correction. Static source assertions checked baseline
ordering, read-only recovery, independent expectations, fresh-data guard and refresh validation.
Compilation, packaging, 605-second listener behavior and process-crash recovery remain
unverified; source assertions are not runtime acceptance evidence.
